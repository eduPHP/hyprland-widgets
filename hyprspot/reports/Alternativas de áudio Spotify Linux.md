# Soloist devolve o som ao hyprspot

A melhor alternativa em novembro de 2026 é o **Spotify Soloist**, cliente Spotify Connect oficial e *headless* lançado em agosto de 2026. Ele roda no Linux sem janela, toca pelo PipeWire e tem uma API WebSocket local para controle e eventos. No benchmark publicado, Soloist mais a ponte MPRIS ocupam **~61 MB de RAM e 3% de CPU**, contra **~922 MB e 10%** do cliente desktop oficial com a janela escondida ([soloist-mpris](https://github.com/TobiasVeiga00/soloist-mpris)). Os mantenedores do librespot, do go-librespot e do Raspotify já mandam as contas afetadas pelo "audio key error" usarem o Soloist ([librespot#1649](https://github.com/librespot-org/librespot/issues/1649), [Raspotify](https://github.com/dtcooper/raspotify)). O motivo é que o bloqueio vem do servidor, não tem contorno conhecido e nenhum projeto vai implementar o PlayPlay por medo de DMCA. Trocar de cliente open-source não resolve. Se o Soloist falhar na conta, ou se o Web API não conseguir transferir a reprodução para ele, sobram dois motores oficiais. O primeiro é o **cliente oficial escondido num workspace especial do Hyprland**: comprovadamente toca em contas afetadas, mas pesa perto de 1 GB. O segundo é o **Web Playback SDK numa instância dedicada do Google Chrome**, que já está instalado com Widevine nesta máquina e tem um projeto de referência em 2026 criado justamente para contornar o mesmo erro, porém exige mais engenharia. Celular com Bluetooth ou AirPlay para o notebook é a saída de emergência. Spicetify é um acessório do cliente oficial e não toca nada sozinho. O controle de transporte deve passar por um canal local (WebSocket do Soloist ou MPRIS, na casa das dezenas de ms). O Web API fica com busca, playlists e transferência, porque desde julho de 2026 a cota do Development Mode é compartilhada por conta de desenvolvedor.

## O bloqueio de chave é do servidor e encerra toda a família librespot

O erro que o usuário vê (`error audio key 0 1`) é a recusa, pelo backend do Spotify, da chave AES legada que o librespot pede para descriptografar o áudio. O README atual do librespot afirma que **contas criadas depois de um corte aparente não obtêm mais as chaves e que não há contorno conhecido** ([librespot](https://github.com/librespot-org/librespot)). O go-librespot rotulou o caso de `spotify-side`. A issue foi **fechada como *not_planned* e fixada em 18/11/2026**, e o mantenedor recusou explicitamente implementar o PlayPlay ([go-librespot#279](https://github.com/devgianlu/go-librespot/issues/279)). A idade da conta não é um critério confiável: contas de 2021–2022 também falham ([spotifast#283](https://github.com/crmne/spotifast/issues/283)). Na mesma máquina, uma conta Premium funciona e outra não ([librespot#1735](https://github.com/librespot-org/librespot/issues/1735)). Os contornos testados pela comunidade não resolvem: zeroconf em vez de OAuth, bitrate 160 ou 320 e reset de credenciais falharam ([go-librespot#279](https://github.com/devgianlu/go-librespot/issues/279), [librespot#1649](https://github.com/librespot-org/librespot/issues/1649)). Nenhum relato testa a ativação via zeroconf a partir do app oficial numa conta afetada. Como o zeroconf só muda a forma de entregar a credencial, e a chave continua sendo pedida pelo mesmo canal recusado, espera-se a mesma falha.

Isso derruba de uma vez spotifyd, spotify-player ([spotify-player#910](https://github.com/aome510/spotify-player/issues/910)), ncspot, Raspotify, Mopidy-Spotify e Music Assistant. A issue do Music Assistant foi fechada com "não há nada que possamos fazer" ([MA#4624](https://github.com/music-assistant/support/issues/4624)). O psst tem núcleo próprio, mas "diretamente inspirado" no librespot, e pelo mesmo caminho de chave é muito provável que também falhe ([psst](https://github.com/jpochyla/psst)). O Spotube não serve: na versão atual ele não toca áudio do Spotify e busca o som em provedores do tipo YouTube por meio de plugins ([Spotube](https://github.com/KRTirtho/spotube)). Os forks com PlayPlay são um beco jurídico. O repositório público de desofuscação foi derrubado por DMCA ([librespot-java#421](https://github.com/librespot-org/librespot-java/discussions/421)) e o CDM PlayPlay do SpotifyDL foi removido após notificação ([TorrentFreak](https://torrentfreak.com/spotify-dismantles-spotifydl-track-download-extension-via-dmca-notice-250429/)). O Spotify registrou novas notificações no GitHub em setembro e novembro de 2026, uma delas citando anticircunvenção ([github/dmca#22111](https://github.com/github/dmca/pull/22111)). O mantenedor do Raspotify resume: **"Spotify will pursue with legal action if the solution is published"** ([raspotify#757](https://github.com/dtcooper/raspotify/issues/757)). Clientes ainda ativos, como spotifast 0.15.0 e spotatui, passaram a usar o Soloist como motor quando o player embutido falha ([spotifast#283](https://github.com/crmne/spotifast/issues/283), [spotatui](https://github.com/LargeModGames/spotatui/blob/main/docs/soloist.md)).

## Soloist é o motor oficial mais leve, com WebSocket local pronto

O Soloist é documentado pelo próprio Spotify como um cliente que **"turns your device into a dedicated Spotify playback device"**. Há builds Linux para x86_64, AArch64 e ARMv7. O áudio sai pelo PipeWire, com fallback para PulseAudio ([Soloist](https://developer.spotify.com/documentation/soloist), [GitHub spotify/soloist](https://github.com/spotify/soloist)). Segundo o anúncio, ele "roda o mesmo motor de reprodução do app Spotify", com lossless e normalização ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/Spotify-Soloist-a-new-terminal-based-player-for-headless-and-DIY/m-p/7529090/highlight/true)). Por isso ele não depende do caminho de chave que o servidor recusa. Não existe, porém, relato público de teste exatamente numa conta com o erro do librespot. A confiança vem de ser cliente oficial e de os mantenedores o recomendarem para esses casos ([librespot#1649](https://github.com/librespot-org/librespot/issues/1649)). Para o hyprspot, o ponto central é a API: com `--ws 127.0.0.1:PORT`, o daemon expõe JSON com eventos `playback_changed`, `volume_changed`, `position_sync` e `queue_changed`, e aceita comandos de play, pause, seek, volume, shuffle, repeat e fila ([referência WebSocket](https://developer.spotify.com/documentation/soloist/reference/websocket-api), [features](https://developer.spotify.com/documentation/soloist/features)). Há também o `soloist ctl` com saída `--json`.

A integração em GTK4/Python é das mais simples. Um cliente WebSocket asyncio, ou um `Gio` com loop de integração, recebe estado por *push* e acaba com o polling de `GET /me/player`. Outra opção é instalar o **soloist-mpris** e usar o MPRIS que o hyprspot já fala. Ele expõe metadados, capa e progresso, além de play/pause, next/prev, seek, **volume, shuffle e repeat** ([soloist-mpris](https://github.com/TobiasVeiga00/soloist-mpris)), coisas que o MPRIS do cliente oficial não entrega. Nenhuma fonte mediu a latência do WebSocket do Soloist. Por ser loopback local, espera-se a mesma ordem de grandeza dos ~25 ms que o hyprspot já mede no MPRIS. Busca e "tocar esta playlist" continuam no Web API: a documentação diz que o Soloist é um dispositivo Connect normal, então `PUT /me/player` com o `device_id` dele deveria funcionar. Nenhuma fonte documenta isso explicitamente, e é o primeiro ponto a testar.

Os custos são operacionais. **Os builds expiram em 90 dias**, cada usuário precisa gerar a própria chave de API no Developer Dashboard com conta Premium e os binários não podem ser redistribuídos ([Soloist](https://developer.spotify.com/documentation/soloist)). O soloist-mpris resolve a expiração com um timer semanal que baixa o build atual ([soloist-mpris](https://github.com/TobiasVeiga00/soloist-mpris)). O WebSocket **não tem autenticação, TLS nem checagem de Origin** ([features](https://developer.spotify.com/documentation/soloist/features)), então deve escutar apenas em 127.0.0.1. Os builds pedem glibc ≥ 2.38, o que o Ubuntu 26.04 atende. Usuários relatam que é preciso escolher "Lossless" no menu Connect, senão o áudio fica em 160 kbps, e alguns com plano Family ou Basic tiveram dificuldade para gerar a chave ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/Spotify-Soloist-a-new-terminal-based-player-for-headless-and-DIY/m-p/7529090/highlight/true)). Uma fonte secundária menciona integrações que marcam o suporte Connect do Soloist como "desativado no momento" ([SpotOn](https://github.com/stiefenm/spoton)). Isso reforça que a transferência via Web API precisa ser verificada antes de qualquer refatoração. O risco de ToS é baixo, porque é produto do próprio Spotify.

## O cliente oficial escondido funciona, mas custa quase 1 GB

O cliente desktop é o único caminho com **prova direta de funcionar em contas afetadas**. Usuários com o erro no go-librespot migraram para ele, e o erro se repetiu mesmo com o app oficial na mesma conta controlando o go-librespot ([go-librespot#279](https://github.com/devgianlu/go-librespot/issues/279)). Snap (publicado pelo Spotify), repositório apt e Flathub (comunitário, não verificado) trazem a mesma versão **1.2.95.453**, e o snap edge foi atualizado em 9/11/2026 ([Snapcraft](https://snapcraft.io/spotify), [Flathub](https://flathub.org/apps/com.spotify.Client)). O próprio Spotify diz que o Linux "não é uma plataforma que suportamos ativamente". Em 2026 houve várias quebras: troca para **Wayland nativo por padrão** com barra de título CSD, rotação da chave de assinatura do apt, exigência de GLIBC 2.38 e crashes no Flatpak ([comunidade Spotify 2026](https://community.spotify.com/t5/Desktop-Linux/Recent-Linux-client-update-changes-2026/td-p/7238778)). No Linux não existe `--minimized`, que só funciona no Windows ([Spicetify CLI flags](https://spicetify.app/docs/development/spotify-cli-flags)). No Hyprland, o caminho prático é uma regra que manda a janela para `special:spotify silent`, receita já usada por outros usuários ([fórum Hyprland](https://forum.hypr.land/t/toggle-special-workspaces-in-hypridle/1559)). A sintaxe de windowrule mudou na 0.53, a versão desta máquina, então confira a wiki da 0.53 antes de escrever a regra. Com a janela escondida, a CPU cai de 27% para 10%, mas a RAM fica em ~922 MB ([soloist-mpris](https://github.com/TobiasVeiga00/soloist-mpris)).

O controle é quase de graça para o hyprspot, que já fala MPRIS com ~25 ms. O cliente expõe `org.mpris.MediaPlayer2.spotify` com transporte e metadados. As fontes históricas mostram três lacunas, sem confirmação para 2026. **Shuffle e LoopStatus não funcionam** ([playerctl#136](https://github.com/altdesktop/playerctl/issues/136)). **A escrita de Volume é ignorada** ([Arch Wiki](https://kiwix.lema.org/archlinux_en_all_nopic_2022-12/A/Spotify)). **OpenUri inicia a reprodução** da faixa ou do primeiro item do contexto ([comunidade Spotify](https://community.spotify.com/t5/Desktop-Linux/DBus-OpenUri-issue/td-p/1376397)), o que é útil para "tocar playlist" sem passar pelo Web API. Na prática, shuffle e repeat vão pelo Web API e o volume vai pelo sink-input do PipeWire. Para as atualizações automáticas, a mitigação padrão é `snap refresh --hold spotify`.

O **Spicetify** só faz sentido se este cliente for o motor escolhido. Ele modifica a UI do cliente e permite extensões com `Spicetify.Player`/`Spicetify.Platform`, que expõem um WebSocket local de estado e comando, como a WebNowPlaying em `localhost:8974` ([Spicetify extensions](https://www.spicetify.app/docs/advanced-usage/extensions), [API wrapper](https://spicetify.app/docs/development/api-wrapper)). Isso supera o MPRIS em riqueza: shuffle, repeat, fila e volume, sem cota. O projeto está ativo (v2.46.7 em 12/11/2026), mas corre atrás de cada build do Spotify, e o suporte a Linux fica uma versão atrás ([releases](https://github.com/spicetify/cli/releases)). Também é uma modificação não autorizada sob termos amplos, que permitem suspender a conta ([Termos de Uso](https://www.spotify.com/us/legal/end-user-agreement/)). Não há bans documentados. Com o Soloist disponível, o Spicetify vira opcional.

## Web Playback SDK roda no Chrome desta máquina, não no WebKitGTK

O SDK **continua disponível em Development Mode**. As mudanças de fevereiro e julho de 2026 não o mencionam, e todos os endpoints Player seguem listados como "still available", inclusive Transfer Playback e Devices ([changelog fev/2026](https://developer.spotify.com/documentation/web-api/references/changes/february-2026), [changelog jul/2026](https://developer.spotify.com/documentation/web-api/references/changes/july-2026)). Os requisitos são Premium completo e o escopo `streaming`. Planos Lite e Mini falham com `account_error` mesmo quando `/me` retorna `premium` ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-not-working-with-Spotify-Lite-Premium-Mini/td-p/7269497)). O WebKitGTK está descartado: nem o build do Ubuntu nem o do runtime GNOME têm EME ([mixmusic#295](https://github.com/fzn0x/mixmusic/issues/295)). Nesta máquina, porém, o **Google Chrome 157 já tem o Widevine CDM 4.10.3112.0** atualizado pelo component updater (verificação local). Há uma prova em 2026 de que o caminho resolve exatamente o problema do usuário: o projeto spotify-connect-speaker foi criado porque librespot, go-librespot e ncspot davam `audio key error (code 1)` numa conta Premium. Ele roda o SDK em **Firefox headless** sob systemd, com servidor local em 127.0.0.1, ponte MPRIS e `media.autoplay.default=0` ([spotify-connect-speaker](https://github.com/theminimalcreator/spotify-connect-speaker)). O castlabs ECS (Electron com Widevine, sem exigência de VMP no Linux) é a opção para quem quer um bundle próprio, ao custo de mais um runtime Chromium ([castlabs](https://github.com/castlabs/electron-releases)).

Para o hyprspot, a arquitetura sairia assim. O Python serve `http://127.0.0.1:PORT/player.html` e um WebSocket (EME exige contexto seguro, e localhost conta). A página entrega o token via `getOAuthToken`, pedindo ao Python um token fresco do fluxo PKCE que o widget já tem. Os eventos `player_state_changed` são empurrados para o widget, e `togglePlay`/`seek`/`setVolume` são executados localmente, sem passar pelo Web API ([referência do SDK](https://developer.spotify.com/documentation/web-playback-sdk/reference)). O Chrome roda com `--app`, perfil dedicado e regra de workspace especial. Escondido, ele continua tocando, porque o throttling intensivo do Chrome só atinge páginas **silenciosas há ≥30 s** ([Chrome blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)). Há quatro atritos. A política de autoplay exige `activateElement()` num gesto do usuário ou um flag de autoplay. **Cada reload gera um novo `device_id`**, o que obriga a transferir de novo. O processo do navegador precisa de supervisão ([spotify-connect-speaker](https://github.com/theminimalcreator/spotify-connect-speaker)). E o Chrome `--headless` historicamente não tem Widevine ([Cypress/lightrun](https://lightrun.com/answers/cypress-io-cypress-provided-chrome-browser-does-not-support-drm-widevine)), então o `--headless=new` precisa ser testado antes de se contar com ele. Ninguém publicou consumo de RAM. A estimativa é de algumas centenas de MB, a medir. A latência local deve ser baixa, mas também não foi medida. A política de desenvolvedor proíbe uso comercial e exige permissão para produtos que "replicam a experiência central" do Spotify ([Developer Policy](https://developer.spotify.com/policy)). Para uso pessoal, tudo bem. Para distribuir o hyprspot publicamente, essa cláusula importa. O Spotify também pode endurecer a exigência de robustez do Widevine L3 quando quiser.

O **web player completo (open.spotify.com) numa janela `--app` do Chrome** é a versão preguiçosa da mesma ideia. Toca, aparece como dispositivo Connect ("This web player") e exporta MPRIS via Media Session. Esse MPRIS do Chromium, porém, **ignora OpenUri, Raise e Quit, mantém o Volume fixo em 1.0 e não tem Shuffle nem LoopStatus** ([Chromium source](https://chromium.googlesource.com/chromium/src.git/+/main/components/system_media_controls/linux/system_media_controls_linux.cc)). Já houve playback interrompido por congelamento de aba ([comunidade Spotify](https://community.spotify.com/t5/Desktop-Windows/Web-Player-Collapsed-Chrome-tab-group-prevents-playback-after/td-p/5301422)). Ele carrega a UI inteira, provavelmente com RAM parecida com a do cliente desktop (não medido). Não oferece nada que o cliente oficial escondido não ofereça melhor. Serve só para um teste de cinco minutos.

## Celular, caixa ou Chromecast resolvem o som, não a confiabilidade

Usar outro dispositivo Connect como player, com o widget só como controle remoto pelo Web API, funciona hoje sem nenhum componente bloqueado. Esse dispositivo pode ser o celular, uma caixa ou um Chromecast. Para trazer o som do celular ao notebook, o WirePlumber já habilita por padrão o papel `a2dp_sink` no Bluetooth ([WirePlumber](https://julian.pages.freedesktop.org/wireplumber/daemon/configuration/bluetooth.html)). No iPhone, o shairport-sync transforma o notebook num receptor AirPlay com saída PipeWire ([shairport-sync](https://github.com/mikebrady/shairport-sync)). O módulo RAOP do PipeWire só envia áudio, não recebe ([PipeWire](https://docs.pipewire.org/page_module_raop_sink.html)). O problema é a presença do dispositivo. Com o app em segundo plano, o celular cai de `/me/player/devices` ou fica inativo cerca de 5 s depois de uma pausa remota ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/Spotify-Web-Api-Device-goes-inactive-after-5-seconds-of-pausing/td-p/6521535)). Quando todos os dispositivos estão inativos, `PUT /me/player` pode devolver **HTTP 500** ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/Endpoint-quot-Transfer-Playback-quot-returns-500-error-when-all/td-p/6594944)). Chromecasts dormindo ficam invisíveis até o app oficial acordá-los ([comunidade Spotify](https://community.spotify.com/t5/Spotify-for-Developers/v1-me-player-devices-returns-empty-array/m-p/5376515/highlight/true)). No iOS, alvos AirPlay nunca aparecem como dispositivos Connect. O controle continua preso aos 0,4–1 s do Web API, somados ao buffer do Bluetooth, e o MPRIS local não enxerga nada. O custo no notebook é praticamente zero e o esforço no widget é mínimo: basta tratar "dispositivo ausente" como estado normal. Para uso diário, é frágil demais.

| Web Playback SDK no Chrome dedicado | Sim, provável (referência 2026 com o mesmo erro, em Firefox) | Não medido (centenas de MB, estimado) | Chamadas locais via ponte WS | Alto: servidor local, página, token, autoplay, supervisão | Política de dev; L3 pode mudar; device_id muda a cada reload |
| Web player em janela Chrome | Sim | Provavelmente próximo do desktop | MPRIS limitado + Web API | Baixo, mas pobre | Congelamento de aba; MPRIS capado |

| Celular/caixa/Chromecast + BT/AirPlay | Sim | ~0 no notebook | 0,4–1 s + buffer BT | Mínimo | Dispositivo some; 500 na transferência |

A recomendação é adotar o **Soloist como motor padrão do hyprspot**, com WebSocket direto para transporte e estado e o Web API para busca, playlists e `PUT /me/player`. O **cliente oficial escondido** fica como fallback já pronto, sem nada novo a programar. O SDK no Chrome só entra se ambos falharem, ou se mais tarde houver motivo para eliminar o binário do Soloist. Em qualquer arquitetura, o hyprspot deve tratar 429 com `reason: QUOTA_EXCEEDED` separado do rate limit comum, porque a cota passou a ser por conta de desenvolvedor ([blog Spotify](https://developer.spotify.com/blog/2026-07-23-web-api-quota-updates)). Também deve parar de usar polling de `/me/player` assim que existir um canal de *push* local. A ordem de testes abaixo começa pelo que decide mais com menos esforço.

| # | Teste | Critério de sucesso | Se falhar |
|---|---|---|---|
| 1 | Gerar a chave Soloist no Dashboard, baixar o build e rodar `soloist --ws 127.0.0.1:PORT --device-name hyprspot`; selecionar o dispositivo pelo app do celular e tocar uma playlist | Áudio sai pelo PipeWire sem erro de chave | Ir para o teste 4 |
| 2 | Com o Soloist ocioso: `GET /me/player/devices`, `PUT /me/player` para o `device_id` dele e `PUT /me/player/play` com `context_uri` de playlist | Transferência e início sem abrir o app do celular | Usar o comando de play/contexto via WebSocket ou `soloist ctl`; se ainda falhar, teste 4 |
| 3 | Medir o round-trip do WebSocket (pause → `playback_changed`) e a RAM com `smem`; instalar o soloist-mpris e testar `playerctl -p soloist shuffle/volume` | Dezenas de ms; RAM < 100 MB | Manter só o WebSocket direto |
| 4 | `snap install spotify` + regra Hyprland 0.53 para `special:spotify silent`; `busctl --user introspect org.mpris.MediaPlayer2.spotify /org/mpris/MediaPlayer2`; testar Shuffle, LoopStatus, Volume e OpenUri com playlist | Toca escondido; mapear o que o MPRIS aceita | Ir para o teste 5 |
| 5 | Protótipo do SDK: no Chrome `--headless=new` e no `--app`, rodar `navigator.requestMediaKeySystemAccess('com.widevine.alpha', …)` e depois uma `player.html` mínima com o escopo `streaming` | `ready` com `device_id` e áudio após a transferência | Tentar Firefox headless, como no spotify-connect-speaker |
| 6 | Emergência: parear o celular com o notebook como `a2dp_sink` (ou shairport-sync no iPhone) e controlar pelo Web API | Áudio estável; o widget sobrevive ao dispositivo sumir | — |

Opcionalmente, um teste de cinco minutos com librespot ativado via zeroconf pelo app do celular encerra a última dúvida sobre essa família. O resultado esperado é a mesma falha `audio key 0 1`.

## Conclusão

A falha do librespot deixou de ser um problema técnico do hyprspot e virou uma decisão de política do Spotify. O Spotify fechou o caminho não oficial e, no mesmo ano, abriu um oficial (Soloist) que é melhor para um widget do que qualquer player open-source jamais foi: daemon sem janela, eventos por *push* e API local documentada. Isso inverte a arquitetura do hyprspot. Antes ele era um controle remoto que dependia de um Web API lento e com cota. Agora pode ser a interface de um motor local, com o Web API reduzido ao que só ele faz: catálogo, playlists e transferência. A dependência nova é a renovação a cada 90 dias e uma chave de desenvolvedor. Esse ônus é previsível e automatizável, ao contrário das quebras do librespot.

A incerteza que resta é concreta e se resolve em uma tarde. Falta confirmar que o Soloist toca nesta conta e que o Web API consegue transferir a reprodução para ele. Se as duas coisas funcionarem, o cliente desktop e o SDK viram planos B documentados, não trabalho a fazer. Se o hyprspot um dia for distribuído, a escolha do Soloist ainda tem uma vantagem: cada usuário gera a própria chave e baixa o próprio build, então o projeto nunca redistribui binário do Spotify nem toca em DRM.
